# Módulo 7 — Estrategia de Inteligencia Artificial Generativa

**Curso:** Desarrollo de Aplicaciones de IA Generativa  
**Duración total del curso:** 30 horas  
**Documento:** Documentación técnica del Módulo 7  
**Versión:** 1.0 — 30/09/2026  
**Público objetivo:** profesionales técnicos, responsables de producto, arquitectura, seguridad, datos y negocio  
**Enfoque:** selección de oportunidades, alineación estratégica, datos, gobernanza, riesgo, métricas y roadmap de adopción

> **Nota de alcance.** El programa original establece para este módulo: identificación de oportunidades de IA generativa; análisis de procesos y brainstorming de casos de uso; definición de objetivos SMART y alineación con la estrategia empresarial; gestión de datos; privacidad y gobernanza; evaluación de riesgos técnicos, éticos, legales y reputacionales; mitigación de sesgos, transparencia y alucinaciones; impacto en usuarios y sociedad; y creación de un roadmap con priorización, fases, recursos y métricas de éxito.
>
> Este documento desarrolla esos contenidos desde una perspectiva de aplicación real. No pretende sustituir asesoramiento legal ni convertir la estrategia en una checklist. El objetivo es disponer de un método repetible para decidir **qué construir, por qué construirlo, con qué controles y cuándo detenerlo**.

# 0. Cambio de pregunta

Hasta M06 la pregunta principal ha sido:

```text
¿Cómo construimos una aplicación de IA generativa?
```

A partir de M07 cambia:

```text
¿Qué merece la pena construir?
¿Por qué?
¿Con qué datos?
¿Qué riesgo aceptamos?
¿Cómo sabremos si funciona?
¿Cómo lo llevamos a producción?
```

Una organización puede tener una excelente arquitectura técnica y fracasar si automatiza el proceso equivocado, no dispone de datos adecuados, no define una baseline, mide “uso” en lugar de valor, ignora costes operativos, crea riesgos superiores al beneficio o no define ownership.

La estrategia de IA generativa conecta:

```text
negocio
+
producto
+
datos
+
tecnología
+
riesgo
+
personas
```

# 1. Resultados de aprendizaje

Al finalizar M07, el participante debería poder:

1. Identificar tareas y procesos con potencial real para IA generativa.

3. Formular correctamente el problema antes de seleccionar tecnología.
4. Establecer objetivos SMART y métricas de resultado.
5. Definir una baseline pre-IA.
6. Separar métricas de modelo, sistema, usuario y negocio.
7. Evaluar valor potencial, viabilidad técnica, preparación de datos y riesgo.
8. Construir una matriz de priorización de casos de uso.
9. Identificar qué datos necesita realmente una aplicación.
10. Evaluar calidad, representatividad, vigencia, procedencia y permisos de datos.
11. Definir data ownership y responsabilidades.
12. Diferenciar prompting, RAG, fine-tuning y automatización tradicional desde una perspectiva estratégica.
13. Construir un registro de riesgos de IA.
14. Aplicar conceptos del NIST AI RMF.
15. Entender el papel de ISO/IEC 42001 como sistema de gestión de IA.
16. Integrar requisitos regulatorios como contexto de diseño.
17. Identificar riesgos técnicos, legales, éticos, reputacionales y operativos.
18. Diseñar controles para alucinaciones, sesgo, privacidad, seguridad y transparencia.
19. Decidir cuándo debe existir human-in-the-loop.
20. Diseñar gates entre idea, PoC, piloto y producción.
21. Estimar TCO más allá del coste por token.
22. Comparar build, buy y managed service.
23. Crear un roadmap de adopción.
24. Definir criterios de go/no-go.
25. Preparar Enterprise GenAI Assistant para una decisión real de despliegue.

# 2. Estrategia no es una lista de herramientas

Una estrategia incorrecta empieza así:

```text
Tenemos que usar LLMs.
¿Qué podemos hacer con ellos?
```

Una estrategia mejor empieza por:

```text
¿Dónde tenemos problemas, fricción,
coste, lentitud, errores o capacidad limitada?
```

Después:

```text
¿qué solución es adecuada?
```

Y solo entonces:

```text
¿necesitamos IA generativa?
```

La IA generativa debe competir con alternativas como software convencional, automatización, búsqueda, reglas, BI, ML clásico o rediseño de procesos.

---

# 3. Technology push vs problem pull

## 3.1. Technology push

```text
Tenemos una tecnología nueva
-> buscamos dónde aplicarla
```

Puede generar innovación, pero también soluciones buscando problemas.

## 3.2. Problem pull

```text
Tenemos un problema medible
-> exploramos alternativas
-> IA generativa es una de ellas
```

En un portfolio empresarial, `problem pull` debería dominar.

---

# 4. La unidad correcta de análisis: la tarea

Un proceso suele ser demasiado amplio.

Ejemplo:

```text
“Atención al cliente”
```

no es un único caso de uso. Puede contener:

- clasificación;
- búsqueda;
- redacción;
- traducción;
- extracción;
- resolución;
- escalado;
- actualización de sistemas.

Analizar a nivel de tarea permite decidir:

```text
automatizar
asistir
mantener humano
```

por separado.

---

# 5. Process decomposition

Ejemplo de gestión de incidente:

```text
1. recibir alerta
2. crear ticket
3. recopilar contexto
4. localizar procedimiento
5. resumir impacto
6. proponer acciones
7. ejecutar cambio
8. comunicar estado
9. cerrar
10. hacer postmortem
```

No todas las tareas necesitan GenAI.

---

# 6. Automatización tradicional primero

Si una tarea es:

```text
if severity == "P1":
    notify_on_call()
```

no necesitamos un LLM.

Una regla determinista es barata, verificable, reproducible y fácil de auditar.

Principio:

> No sustituir lógica determinista por probabilística sin una razón.

---

# 7. Señales de buen encaje para GenAI

Tareas donde aparece:

- texto no estructurado;
- variabilidad lingüística;
- síntesis;
- transformación;
- búsqueda semántica;
- generación de borradores;
- clasificación compleja;
- extracción flexible;
- conocimiento distribuido;
- interacción conversacional.

---

# 8. Señales de mal encaje

Tareas que requieren:

- exactitud matemática absoluta;
- autorización;
- ejecución determinista;
- reglas simples;
- muy baja tolerancia a error;
- latencia extremadamente estricta;
- outputs que ya existen en una base estructurada.

En esos casos:

```text
software tradicional
+
IA como asistencia opcional
```

puede ser mejor.

---

# 9. Human augmentation vs replacement

Pregunta estratégica:

```text
¿queremos sustituir una tarea
o aumentar la capacidad de una persona?
```

Muchas primeras implantaciones obtienen más valor con:

```text
copilot
```

que con:

```text
autonomous agent
```

# 10. Escalera de autonomía

Podemos definir niveles internos:

## Nivel 0 — Manual

```text
humano hace todo
```

## Nivel 1 — Información

```text
IA busca / resume
humano decide
```

## Nivel 2 — Recomendación

```text
IA propone
humano aprueba
```

## Nivel 3 — Ejecución supervisada

```text
IA prepara acción
humano autoriza
sistema ejecuta
```

## Nivel 4 — Ejecución automática limitada

```text
IA ejecuta dentro de boundaries
```

## Nivel 5 — Alta autonomía

```text
IA decide y actúa ampliamente
```

Mayor autonomía implica mayores exigencias de evaluación, observabilidad, permisos, rollback y accountability.

# 11. Identificación de oportunidades

Tres fuentes habituales:

```text
pain points
volumen
conocimiento
```

## 11.1. Pain points

Preguntar:

- ¿qué tarda demasiado?;
- ¿qué genera errores?;
- ¿qué requiere copiar/pegar?;
- ¿qué obliga a buscar en muchos sitios?;
- ¿qué produce retrabajo?;
- ¿qué depende de pocas personas expertas?

## 11.2. Volumen

Una mejora pequeña multiplicada por gran volumen puede generar mucho valor.

Ejemplo:

```text
2 min ahorrados
×
50 000 casos/año
=
100 000 min
```

≈ 1 667 horas.

## 11.3. Cuello de botella experto

Ejemplo:

```text
500 empleados
+
3 expertos que responden siempre las mismas dudas
```

Un asistente con RAG puede aumentar capacidad, sin sustituir necesariamente al experto.

Síntoma:


Buen candidato para:

```text

```

# 13. Content friction

Síntoma:

```text
gran cantidad de borradores repetitivos
```

Ejemplos:

- comunicaciones;
- informes;
- propuestas;
- documentación;
- resúmenes.

---

# 14. Data transformation friction

Ejemplo:

```text
email
-> extraer campos
-> sistema
```

Puede resolverse con structured output, sin necesidad de un chatbot.

# 17. Problema antes de solución

Mala descripción:

```text
“Chatbot con GPT”
```

Buena descripción:

```text
“Los ingenieros tardan una media de 12 minutos
en localizar el procedimiento correcto para
incidentes P1.”
```

Solución candidata:

```text
RAG assistant
```

# 18. Usuario y job-to-be-done

Un caso sin usuario definido suele estar mal formulado.

Pregunta:

> ¿Qué intenta conseguir realmente la persona?

No:

```text
“consultar un chatbot”
```

Sí:

```text
“encontrar rápidamente el procedimiento vigente
para responder a un incidente”
```

# 19. Baseline

Antes de introducir IA debemos medir el proceso actual.

Ejemplos:

```text
tiempo medio
coste/caso
errores
retrabajo
escalados
satisfacción
throughput
```

Sin baseline:

```text
no podemos demostrar mejora
```

---

# 20. Objetivos SMART

SMART:

```text
Specific
Measurable
Achievable
Relevant
Time-bound
```

Objetivo incorrecto:

```text
“Mejorar el soporte con IA.”
```

Objetivo mejor formulado:

```text
Reducir en un 30% el tiempo mediano que los técnicos
de soporte emplean en localizar procedimientos vigentes
durante incidentes P1, sin aumentar la tasa de respuestas
incorrectas, durante un piloto de 8 semanas.
```

---

# 21. Métricas en cuatro capas

Una arquitectura práctica:

```text
MODEL
SYSTEM
USER
BUSINESS
```

## Model

- factuality;
- retrieval hit;
- citation validity;
- exact match;
- hallucination rate.

## System

- latency;
- availability;
- errors;
- throughput;
- cost/request.

## User

- task completion;
- satisfaction;
- time saved;
- acceptance rate;
- override rate.

## Business

- cost saved;
- revenue;
- risk reduction;
- SLA improvement;
- capacity increase.

---

# 22. North Star y counter-metrics

Una métrica principal debe estar alineada con el resultado.

Ejemplo:

```text
time-to-authoritative-answer
```

No:

```text
tokens consumed
```

Pero optimizar una métrica puede empeorar otras.

Ejemplo:

```text
Objetivo:
reducir tiempo de respuesta

Counter-metrics:
errores
escalados incorrectos
incidentes de seguridad
satisfacción
```

---

# 23. Adoption no equivale a éxito

Un sistema muy usado puede generar retrabajo.

Un sistema poco usado puede resolver un caso crítico de alto valor.

Medir resultado, no únicamente utilización.

---

# 24. Acceptance rate

Para un borrador:

```text
aceptado sin cambios
aceptado con cambios
rechazado
```

Esta señal suele ser más útil que contar prompts.

Preguntar:


Ejemplos:

- eficiencia;

- calidad;
- seguridad;

```text
Business capability

       ↓
```
