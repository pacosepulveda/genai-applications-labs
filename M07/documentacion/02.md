# 26. Sponsorship y ownership

Un caso de uso necesita varios responsables.

## Sponsor

Desbloquea recursos y conecta con la estrategia.

## Product Owner

Responsable de problema, usuario, backlog y valor.

## Technical Owner

Responsable de arquitectura y operación técnica.

## Risk Owner

Responsable de gestionar/aceptar riesgos.

## Data Owner

Responsable del uso, calidad, acceso y clasificación de datos.

Caso de uso sin owner:

```text
PoC eterno
```

# 27. Priorización de iniciativas

No priorizar por:

```text
“esto parece impresionante”
```

Evaluar dimensiones como:

- business value;
- strategic alignment;
- data readiness;
- technical feasibility;
- user readiness;
- risk;
- time-to-value.

# 28. Matriz valor/esfuerzo

```text
               HIGH VALUE
                   |
        QUICK WIN  | STRATEGIC BET
                   |
LOW EFFORT --------+-------- HIGH EFFORT
                   |
       LOW PRIORITY| HEAVY INVESTMENT
                   |
```

# 29. Scoring no debe ocultar juicio

Un score:

```text
82/100
```

parece preciso, pero depende de pesos y supuestos.

La matriz sirve para discusión.

No sustituye decisión.

# 30. Risk-adjusted value

Podemos expresar conceptualmente:


a) valor esperado;  
b) viabilidad;  
c) riesgo residual.

Una fórmula posible:

\[
Priority = Value \times Feasibility \times RiskAdjustment
\]

Debe utilizarse como instrumento de conversación, no como verdad matemática.

# 36. Data quality

Dimensiones tradicionales:

- completeness;
- accuracy;
- consistency;
- timeliness;
- uniqueness;
- validity.

En GenAI añadimos:

- extraction quality;
- OCR quality;
- chunkability;
- metadata completeness;
- duplicate documents;
- conflicting versions.

# 37. Garbage in, plausible prose out

En sistemas clásicos:

```text
bad data
-> bad output
```

En GenAI:

```text
bad data
-> output convincente
```

Esto puede ser más peligroso.

# 38. Representatividad

El dataset debe representar:

- idiomas;
- regiones;
- usuarios;
- escenarios;
- edge cases.

Si el eval set solo contiene ejemplos sencillos obtenemos falsa confianza.

---

# 39. Cantidad no sustituye calidad

Más datos no equivale automáticamente a mejor sistema.

Ejemplo:

```text
1 millón de documentos obsoletos
```

puede ser peor que:

```text
10 000 documentos curados
```

---

# 40. Freshness

Clasificar fuentes:

```text
static
daily
realtime
```

El mecanismo debe ajustarse.

RAG puede sincronizar documentos.

Tools pueden consultar sistemas en tiempo real.

---

# 41. RAG vs fine-tuning

Desde la estrategia de datos:

## RAG

Adecuado para:

- conocimiento cambiante;
- fuentes citables;
- corpus privado.

## Fine-tuning

Adecuado para:

- comportamiento;
- formato;
- estilo;
- tarea repetitiva.

No usar fine-tuning como base de datos.

---

# 42. Prompting vs fine-tuning

Empezar habitualmente por:

```text
prompt + eval
```

Fine-tuning si existe evidencia de que prompting no alcanza el objetivo y disponemos de dataset adecuado.

---

# 43. Data minimization

No utilizar todo el data lake porque esté disponible.

Usar lo necesario para la finalidad reduce:

- privacidad;
- coste;
- ruido;
- exposición.

---

# 44. Purpose limitation y privacidad

Dato recogido para finalidad A no siempre debe reutilizarse para B.

Revisar:

- base jurídica;
- contrato;
- expectativas de usuario;
- finalidad;
- retención.

Identificar PII:

- nombres;
- emails;
- teléfonos;
- IDs;
- biometría;
- categorías especiales.

---

# 45. Secrets no son datos de contexto

Contraseñas, tokens, API keys y claves privadas no deben tratarse como contexto normal del modelo.

Principio:

```text
secret minimization
```

# 48. Retención y feedback

No guardar indefinidamente prompts, outputs o traces sin necesidad.

El feedback tipo thumbs-up/down es débil.

Mejor capturar:

```text
qué estaba mal
qué corrigió
qué fuente faltó
```

No convertir automáticamente todo feedback en datos de fine-tuning.

# 49. Data readiness levels

Modelo interno de madurez:

```text
D0 -> datos desconocidos
D1 -> inventariados
D2 -> accesibles
D3 -> curados y con metadata
D4 -> evaluados para el caso
D5 -> operacionalizados y monitorizados
```

Un caso de gran valor puede quedar en `NOT YET` porque necesita D4 y solo dispone de D1.

# 50. Gobernanza de IA

Governance responde:

```text
quién decide
qué está permitido
cómo se controla
cómo se demuestra
```

No significa un comité que bloquea toda innovación.

La gobernanza eficaz debe permitir experimentación segura.

# 51. Governance by design

Los controles deben incorporarse desde discovery.

No añadirse el día anterior al despliegue.

# 52. NIST AI RMF

NIST AI RMF organiza la gestión del riesgo en cuatro funciones:

```text
GOVERN
MAP
MEASURE
MANAGE
```

Govern es transversal.

## GOVERN

- políticas;
- roles;
- accountability;
- risk tolerance;
- procesos.

## MAP

- propósito;
- usuarios;
- afectados;
- datos;
- contexto;
- impactos.

## MEASURE

- calidad;
- seguridad;
- bias;
- reliability;
- performance;
- impacto.

## MANAGE

- priorizar;
- tratar;
- aceptar;
- monitorizar.

El AI RMF no es una checklist secuencial.

# 67. EU AI Act — contexto a 30/09/2026

El Reglamento (UE) 2024/1689 tiene un calendario progresivo.

A la fecha de este documento:

- las prohibiciones, definiciones y obligaciones relacionadas con AI literacy comenzaron a aplicarse en 2025;
- las reglas de gobernanza y obligaciones para determinados proveedores de GPAI comenzaron a aplicar en 2025;
- desde **2 de agosto de 2026** son aplicables, entre otras, obligaciones de transparencia del artículo 50;
- la Comisión y autoridades nacionales disponen ya de competencias de enforcement para determinadas disposiciones;
- los requisitos para categorías de alto riesgo tienen fechas posteriores según el tipo de sistema.

No debemos convertir esto en:

```text
“el AI Act aplica igual a todo chatbot”
```

Hay que determinar:

- rol de la organización;
- categoría del sistema;
- contexto de uso;
- población afectada;
- obligaciones concretas.
