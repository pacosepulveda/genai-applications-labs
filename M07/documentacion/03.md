# 70. Explainability vs generated explanation

Un LLM puede explicar su respuesta.

Eso no significa que la explicación sea una representación fiel de su proceso interno.

En aplicaciones prácticas suele ser más útil la trazabilidad:

```text
input
sources
tool calls
model version
policy
output
```

---

# 71. Bias y fairness

Sesgo puede venir de:

- training data;
- prompts;
- retrieval;
- labels;
- sampling;
- user population.

La evaluación debe mirar subgrupos, no solo promedios.

No existe una única métrica universal de fairness.

---

# 72. Impacto ético y social

Preguntas:

- ¿puede manipular?;
- ¿crea dependencia?;
- ¿reduce autonomía humana?;
- ¿afecta oportunidades?;
- ¿desplaza tareas?;
- ¿genera deskilling?

No todo lo legalmente permitido es automáticamente deseable.

---

# 73. Human oversight

No basta escribir:

```text
“human in the loop”
```

Hay que definir qué revisa la persona.

Patrones:

## Review before publication

```text
IA genera -> humano publica
```

## Approval before action

```text
IA propone -> humano aprueba -> tool ejecuta
```

## Exception review

```text
IA maneja casos simples -> humano revisa excepciones
```

---

# 74. Automation bias y human fatigue

Usuarios pueden aceptar resultados porque los produjo la IA.

Pero si un humano debe aprobar 10 000 outputs diarios, la revisión puede convertirse en rubber-stamping.

El human oversight debe ser viable y proporcional al riesgo.

---

# 75. Business continuity

Pregunta:

```text
¿Qué ocurre si el proveedor de IA no está disponible durante 4 horas?
```

Casos importantes necesitan:

- modo degradado;
- fallback;
- runbook;
- kill switch.

---

# 76. Kill switch y rollback

Debemos poder deshabilitar una feature de IA sin detener toda la aplicación.

Versionar:

- model;
- prompt;
- index;
- policies;
- tool configuration.

Así podemos hacer rollback.

---

# 77. Evaluación continua

No basta evaluar antes del launch.

Necesitamos monitorizar:

- calidad;
- drift;
- retrieval;
- coste;
- abuso;
- incidentes;
- user feedback.

---

# 78. Model drift, knowledge drift y user drift

## Model/provider drift

Comportamiento puede cambiar tras actualización.

## Knowledge drift

El corpus cambia.

## User drift

Usuarios encuentran usos nuevos, previstos o no previstos.

Los tres deben vigilarse.

---

# 79. Red teaming

Antes de producción probar:

- adversarial prompts;
- injection;
- jailbreak;
- data leakage;
- unsafe actions.

La intensidad del red teaming debe ser proporcional al impacto/autonomía.

---

# 80. Evaluation vs monitoring

## Evaluation

Experimentos controlados.

## Monitoring

Comportamiento real en producción.

Necesitamos ambos.

---

# 81. Creación del roadmap

Un roadmap no es una lista de features.

Debe incluir:

- fases;
- learning goals;
- gates;
- dependencias;
- owners;
- recursos;
- métricas.

---

# 82. Fase 0 — Discovery

Objetivo:

```text
¿merece investigarse?
```

Entregables:

- use case card;
- baseline;
- sponsor;
- initial risk;
- data inventory.

Gate 0:

Go si existe problema real, valor plausible, owner, datos potenciales y riesgo no prohibitivo.

---

# 83. Fase 1 — Feasibility / Prototype

Objetivo:

```text
¿puede funcionar técnicamente?
```

No optimizar producción todavía.

Un prototipo debe responder una pregunta técnica concreta.

Ejemplo:

```text
¿podemos alcanzar Hit Rate@3 >= 0.90
sobre procedimientos internos?
```

---

# 84. Fase 2 — PoC

Objetivo:

```text
¿funciona en condiciones representativas?
```

Añadir:

- muestra de datos reales;
- usuarios representativos;
- eval suite;
- costes;
- seguridad inicial.

Anti-patrón:

```text
demo con cinco preguntas preparadas
```

---

# 85. Fase 3 — Pilot

Usuarios reales y alcance limitado.

Objetivo:

```text
medir valor real
```

Definir:

- población;
- duración;
- baseline;
- soporte;
- feedback;
- rollback;
- métricas.

---

# 86. Fase 4 — Production

Antes del go-live deben estar definidos:

- KPI achieved;
- residual risk accepted;
- monitoring;
- support;
- incident process;
- documentation;
- training;
- ownership.

Producción no significa “terminado”.

---

# 87. Fase 5 — Scale

Preguntar:

```text
¿puede reutilizarse?
```

Expandir:

- usuarios;
- países;
- departamentos;
- features.

Reevaluar riesgo.

---

# 88. Stage gates

```text
IDEA
 ↓ G0
FEASIBILITY
 ↓ G1
POC
 ↓ G2
PILOT
 ↓ G3
PRODUCTION
 ↓ G4
SCALE
```

Cada gate necesita criterios explícitos.

# 89. Stop criteria

Definir también cuándo parar.

Ejemplo:

```text
si grounded accuracy < 85%
tras tres iteraciones razonables
```

no continuar indefinidamente.

Un PoC fallido puede ser un éxito si evita un proyecto caro.

---

# 90. Resource planning

No estimar solo coding.

También:

- data preparation;
- eval;
- integration;
- security;
- legal;
- governance;
- user testing;
- operations.

M08 profundizará en roles y equipos.

# 91. Build, buy o assemble

Tres opciones:

```text
build
buy
assemble
```

La mayoría de aplicaciones GenAI empresariales serán `assemble`.

Ejemplo:

```text
managed LLM
+
own RAG
+
own policy
+
own UI
```

---

# 92. Build

Adecuado cuando existe diferenciación estratégica, control requerido o necesidad única.

Coste:

- tiempo;
- mantenimiento;
- skills;
- operación.

---

# 93. Buy

Adecuado para capabilities commodity y rapidez.

Riesgos:

- lock-in;
- integración;
- datos;
- poca personalización.

---

# 94. Modelo propio vs gestionado

Pregunta estratégica:

```text
¿el modelo es nuestra ventaja competitiva?
```

Si no, un modelo gestionado puede ser más razonable.

No debemos confundir:

```text
aplicación diferenciadora
```

con:

```text
necesidad de entrenar foundation model propio
```

---

# 95. Multi-model

No necesitamos un modelo para todo.

Ejemplo:

```text
small model -> clasificación
larger model -> reasoning/generation
embedding model -> retrieval
```

Pero cada variante aumenta evaluación y operación.

---

# 96. Vendor lock-in

No siempre es negativo.

Puede aceptarse si:

```text
beneficio > coste
```

Lo importante es que sea una decisión consciente.

---

# 97. TCO

No es solo:

```text
€/1M tokens
```

Incluye:

```text
model inference
embeddings
storage
vector DB
compute
network
observability
licenses
engineering
support
governance
human review
```

---

# 98. Cost/request vs cost/task

Más útil que coste por request:

```text
cost per successfully completed task
```

Si el 50% de respuestas requiere retrabajo, un coste de token bajo puede ser engañoso.

---

# 99. Productivity capture

Tiempo liberado no significa coste eliminado.

Puede significar:

- más capacidad;
- mejor calidad;
- menos backlog.

El business case debe especificar cómo se captura el valor.

---

# 100. ROI y sensibilidad

\[
ROI = \frac{Benefit - Cost}{Cost}
\]

Pero beneficio puede incluir:

- revenue;
- capacity;
- risk avoided;
- quality.

Construir escenarios:

```text
Conservative
Base
Optimistic
```

Variar:

- adoption;
- accuracy;
- cost/token;
- time saved.
