# 72. AI Incident

Un sistema puede estar:

```text
HTTP 200
```

y estar funcionando mal porque responde con información incorrecta.

Necesitamos incident taxonomy:

- provider outage;
- retrieval degradation;
- unauthorized access;
- data leakage;
- runaway cost;
- unsafe tool call.

# 73. Quality SLOs

Además de uptime podemos vigilar:

```text
citation validity
unauthorized retrieval rate
tool success
```

Son más difíciles de medir, pero describen mejor el servicio.

# 74. Runbooks

Ejemplos:

- disable model;
- switch provider;
- rebuild index;
- disable agent;
- revoke tool.

# 75. Postmortem

Un incidente AI debe producir:

- timeline;
- technical cause;
- process/control failure;
- action items;
- nuevos eval cases.

# 76. FinOps Operacional

Dashboard por:

- product;
- team;
- model;
- environment.

Detectar:

```text
token spikes
agent loops
unexpected embedding jobs
```

Cost optimization debe coordinarse con Product para no reducir quality de manera ciega.

# 77. Silos

Silos frecuentes:

```text
Data
Application Development
Security
Cloud
Business
```

La solución no es crear un silo nuevo llamado “AI”.

# 78. Shared outcomes

Alinear equipos con:

```text
task success
```

en lugar de outputs departamentales.

Ejemplo:

No:

```text
Data entregó índice
AI entregó prompt
```

Sí:

```text
usuario encuentra fuente correcta en <7 min
```

# 79. Governance bottleneck

Si cada experimento necesita semanas de approval:

```text
shadow AI
```

aumentará.

Usar fast lanes para patrones de bajo riesgo y revisiones profundas para excepciones.

# 80. PoC Factory

Antipatrón:

```text
muchas demos
pocos servicios
```

Causas:

- no owner;
- no platform;
- no data governance;
- no operations;
- sin metrics.

Número de PoCs no es un KPI de éxito.

# 81. Research-to-production gap

Notebook:

```text
funciona
```

Producción añade:

```text
reliability
security
cost
support
```

# 82. Change Management organizativo

La tecnología cambia trabajo.

Necesitamos:

- comunicación;
- formación;
- feedback;
- champions;
- incentivos coherentes.

Resistencia no significa ignorancia: puede revelar mala UX, riesgos reales o incentivos incorrectos.

# 83. Champions

Usuarios avanzados pueden ayudar a:

- pilotar;
- enseñar;
- identificar gaps.

No sustituyen support formal.

# 84. Adoption y feedback

Capturar:

```text
accepted
edited
rejected
missing source
wrong source
```

No incentivar uso de IA como fin en sí mismo.

# 85. Sponsorship ejecutivo

Un buen sponsor:

- conecta con estrategia;
- resuelve blockers;
- financia capabilities;
- legitima cambio.

Un steering group debe mirar:

- portfolio;
- value;
- risk;
- cost.

No decidir prompts.

# 86. Separation of Duties

No concentrar en una misma persona:

```text
developer
approver
risk acceptor
production admin
```

cuando el impacto es alto.

En equipos pequeños una persona puede llevar varios sombreros, pero las responsabilidades siguen existiendo y deben hacerse explícitas.

# 87. Minimum Viable AI Team

Para un producto GenAI empresarial típico:

```text
Product
AI/Software Engineering
Data/Knowledge Engineering
Domain Expert
Platform/Security support
```

No significa cinco FTE.

Añadir MLOps, SRE, UX, Research o Risk según los bottlenecks.

# 88. Conway's Law

La arquitectura tiende a reflejar las estructuras de comunicación.

Si cada función está aislada:

```text
el sistema también estará fragmentado
```

Definir APIs organizativas y técnicas entre:

- model gateway;
- knowledge service;
- policy;
- product teams.

# 89. Ownership Map

Cada componente productivo debería responder:

```text
owner?
repo?
dashboard?
SLO?
on-call?
runbook?
```

# 109. Maturity Model

## M0 — Ad hoc

Experimentos individuales.

## M1 — Repeatable

Git + prácticas básicas.

## M2 — Managed

Owners + CI/CD + evals.

## M3 — Platformed

Self-service + shared capabilities.

## M4 — Optimized

Portfolio + cost + continuous quality.

Madurez significa capacidades, no cantidad de herramientas compradas.
